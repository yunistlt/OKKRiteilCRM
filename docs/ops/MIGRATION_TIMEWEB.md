# Переезд с Vercel на свой сервер Timeweb

Решение владельца 22.10.2026, после простоя из-за прокси перед Vercel.
Работы — **пятница 23.10.2026, 20:00 МСК**, когда отдел не работает.

Порядок жёсткий: **сначала полностью переезжаем и тестируем, переключаем людей
только если всё хорошо.** До переключения прод продолжает работать на Vercel.

## Что есть сейчас

| | |
|---|---|
| Приложение | Next.js 14 (App Router), сборка на Vercel |
| Путь запроса | браузер (РФ) → VPS `5.42.111.117` (nginx) → Vercel `76.76.21.21` |
| Кроны | 52 штуки в `vercel.json` |
| Переменные окружения | 19 |
| База | Supabase (внешняя) — **не переезжает** |
| VPS | Timeweb «OKKRiteil», 2 CPU / 4 ГБ / 50 ГБ, Ubuntu 24.04, Node 18 |

Почему переезжаем: стык «прокси → Vercel» 22.10.2026 положил сервис на час —
nginx упирался в лимиты, Vercel при этом был жив. Убираем звено целиком.

## Этап 0. Подготовка (до пятницы, прод не трогаем)

1. `next.config.js` → `output: 'standalone'` (сборка едет одним каталогом).
2. Node 20 LTS на VPS (сейчас 18; локально проект на 24).
3. Сборку делает GitHub Actions и привозит архив по ssh: на 4 ГБ собирать рядом
   с работающим приложением нельзя — памяти впритык.
4. `deploy.sh` на VPS: распаковать, переключить симлинк `current`, `systemctl restart`.
5. `systemd`-юнит `okk.service` (Node, порт 3000, автозапуск, перезапуск при падении).
6. 52 крона → один `systemd`-таймер-диспетчер или `/etc/cron.d/okk` с тем же
   `CRON_SECRET` в заголовке. **Пока выключены.**
7. Перенести 19 переменных окружения в `/etc/okk.env` (права 600).

Риск этапа: нулевой — ничего работающего не трогаем.

## Этап 1. Переезд (пятница 20:00)

1. Выкатить сборку на VPS, поднять на **порту 3000**, людям он не виден.
2. Открыть временно `https://okk.zmksoft.com:8443` (отдельный server в nginx,
   тот же сертификат) — для проверки.
3. Прогнать миграции не нужно: база одна и та же.

Откат: просто не переключаем nginx. Vercel работает как работал.

## Этап 2. Проверка (сразу после, по списку)

Проверяем на `:8443`, глядя в ту же боевую базу:

- [ ] вход, роли: админ, РОП, менеджер;
- [ ] список заказов: фильтры, статусы, скорость (норма — доли секунды);
- [ ] карточка заказа: правка, состав, статусы, файлы, история;
- [ ] письма: лента, отправка, вложения, «Загрузить историю»;
- [ ] звонки: список, запись, всплывающее окно входящего (вебсокет);
- [ ] мессенджер: сообщения и web-push;
- [ ] виджет «Елена» на zmktlt.ru (через временный адрес);
- [ ] Семён: ответ по базе знаний;
- [ ] зарплата: ведомость за период;
- [ ] каждый крон — по одному вызову руками, ответ 200 и запись в журнал.

Не прошло — переключение отменяется, разбираемся, прод на Vercel.

## Этап 3. Переключение (только если этап 2 чистый)

1. В nginx `proxy_pass` → `http://127.0.0.1:3000` (одна строка).
2. `nginx -t && systemctl reload nginx` — без обрыва запросов.
3. Кроны: **сначала выключить `crons` в `vercel.json`** и выкатить это на
   Vercel, только потом включить таймеры на VPS. Иначе задачи пойдут дважды.
4. Вебхуки Телфина и виджета менять не нужно: адрес тот же.
5. Egress Т-Банка (`/tbank-egress-…`) остаётся на этом же nginx как есть.

Откат (минута): `proxy_pass` обратно на `76.76.21.21`, `reload`, вернуть
`crons` в `vercel.json`. Деплой на Vercel держим неделю, не удаляем.

## Этап 4. Неделя наблюдения

- Сторож на VPS уже есть (`ops/watchdog`) — добавить проверку `okk.service`.
- Смотрим: память (4 ГБ на всё приложение), время ответа, перезапуски сервиса.
- Если упираемся в память или CPU — увеличиваем тариф VPS, это делается за минуты.

## Чего переезд НЕ решает

- **База.** Supabase остаётся там же: медленный диск и тяжёлые запросы никуда
  не денутся (закон проекта про план запроса до запуска — в силе).
- **Единая точка отказа.** Сейчас падает прокси, станет падать всё сразу.
  Поэтому автозапуск, сторож и готовый откат на Vercel — обязательны.
- Автомасштабирования больше нет: нагрузку держит один сервер.

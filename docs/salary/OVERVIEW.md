# Модуль ЗП ОП — как устроено (as-built)

> Канонический обзор реализованного модуля зарплаты. **Будущие чаты по зарплате начинают отсюда.**
> Дополняет [TZ.md](TZ.md), [PLAN.md](PLAN.md), [DECISIONS.md](DECISIONS.md). Дизайн/код — по [/golds](../../golds/).
> Если код разошёлся с этим документом — обнови документ.

## 1. Что это
Расчёт месячной зарплаты менеджеров отдела продаж в CRM на базе данных RetailCRM/ОКК.
Сейчас работает на **конструкторе бонус-блоков**: модель оплаты каждого менеджера = набор настраиваемых
блоков, собираемых из палитры. Доступ — роли `admin`/`rop`; менеджер видит только свою ЗП (`/salary/my`).

## 2. Главные принципы (инварианты — не нарушать)
1. **Ноль хардкода.** Все ставки/пороги/тиры/оклады — в БД, версионируются по дате (effective-dated).
   В коде — только метод расчёта, не числа. Отсутствующий runtime-параметр = явная ошибка.
2. **Только существующие данные.** Блок объявляет нужные метрики; требовать метрику вне
   `metrics-catalog` нельзя (структурный запрет «несуществующих показателей»).
3. **Реестр ОП = у кого есть назначенная схема** (`salary_manager_comp`). Никто лишний не считается
   (логисты/инженеры/уволенные — вне расчёта, пока им не назначена схема).
4. **Язык:** весь UI и пояснения — на русском. Технические коды (slug статусов и т.п.) — латиницей.
5. **Дизайн — по голдам** (Metro/High-Density: плоско, 0px радиус, без теней, плотно, edge-to-edge).
6. **Закрытый период неизменяем** — `recalc` бросает на закрытом периоде; правки только корректировками.
   Версии схем/конфига/планов с будущим `effective_from` не меняют прошлые периоды.

## 3. Поток данных
```
RetailCRM/ОКК (orders, order_history_log, okk_order_scores, salary_duty)
   │   ← RPC: salary_counted_orders / salary_incoming_counts / salary_client_deal_counts
   ▼
collectPeriodMetrics()  →  ManagerMetrics[] (заказы, типы, качество, конверсия, скидки, дежурства)
   +  resolveManagerComp(asOf)  → у кого какая схема (реестр) + блоки с параметрами
   +  getPlansForPeriod()       → личные/общий планы
   ▼
computePeriodSalary() → для каждого менеджера реестра compose(блоки) = формула
   ▼
salary_calc (legacy-колонки + breakdown.blockContributions)  →  GET /api/salary  →  UI
```
Файлы: `lib/salary/metrics.ts` (сбор), `lib/salary/schemes.ts` (резолв схем/планов),
`lib/salary/blocks/*` (каталог+compose), `lib/salary/engine.ts` (оркестрация+персист).

**Чтение расчёта — единый `loadPeriodView` (`lib/salary/period-view.ts`):**
- **Открытый период — считается НА ЛЕТУ** при каждом заходе (`calculatePeriod`, без
  записи в БД). Заказы, ушедшие в производство только что, сразу в ведомости — без ручной
  кнопки «Пересчитать» и без Vercel-крона. `needsRecalc` для открытого периода всегда `false`.
- **Закрытый период — из снимка** `salary_calc`/`salary_engineer_calc` (неизменяем, инвариант 6).
- Все потребители читают через `loadPeriodView` (единый источник, snapshot и live — одной формы
  через `salaryResultToCalcRow`): список `/api/salary`, «Моя ЗП» `/api/salary/my`, экспорт,
  AI-консультант `consultant-tools.ts`. Раскрытие заказов (`buildTeamOrders`) и конверсия отдела
  (`my-dashboard`) кормятся live-строками. `includeEngineers:false` на «горячих» роутах (/my, консультант).
- `salary_calc` теперь пишется только `recalcAndPersist` (кнопка «Пересчитать») и при закрытии —
  это снимок на момент закрытия, не источник для открытого периода.

### 3a. Исключения из конверсии (знаменатель = входящие заявки)
Живут в **одном месте на два языка**: TS `lib/salary/tender-duplicates.ts` (раскрытие
ведомости) и SQL `salary_incoming_counts` / `salary_counted_orders`
(`migrations/20260729_salary_duplicate_by_items.sql`). **Логика обязана быть зеркальной** —
иначе процент и пояснение под заказом разойдутся. Все коды — в `salary_config`
(`tender_duplicate_rule`, `not_our_product_rule`, `cancel_reason_field`,
`conversion_excluded_statuses`, `request_duplicate_rule`, `estimate_rule`), в коде их нет.

| Исключение | Условие |
|---|---|
| Спам-заявка | статус из `conversion_excluded_statuses`, безусловно |
| Не наша продукция | статус «Нет таких позиций» **или** одноимённая причина отмены |
| Дубль на тендер | номер эталона + общий товар по **наименованию и количеству** + первоисточник в «тендерном» статусе или уже в производстве. **И из числителя тоже** |
| Дубль заявки | статус-дубль + номер существующего эталона + текст причины (и из числителя тоже) |
| Смета | статус «Согласование отмены» + причина отмены «Смета» **или** слово-маркер в комментарии с подтверждением по диалогу. **И из числителя тоже** |

Пять вещей, о которые правило спотыкалось до июля 2026 (разбор ОКК, менеджер Матвеева) —
не повторять при правках:
- **Сравнение по сумме.** Прежнее условие «Σ(цена без скидки × кол-во) совпадает»
  не выживает: тендер разбит по лотам, доставка отдельной строкой (53827), округление
  в 1 ₽ на позицию (53977). Сравниваем состав, а не деньги.
- **Товар — не только артикул.** В каталоге CRM бывают ДВЕ карточки одной номенклатуры
  (у одной артикул человеческий, у другой числовой код): 53760 против 53757/53761 —
  «СССЛ2.ЛП.МД.50.2000.1730.500» против «49407» при одинаковых `xmlId` и названии.
  `orderItemKeys` выдаёт на позицию несколько ключей — по `xmlId`, `article`, `externalId`;
  совпадение по любому + количество = тот же товар.
- **Цепочка дублей.** Эталон сам может быть дублем (53886 → 53873 → 53478) —
  разворачиваем до первоисточника (`resolveDuplicateRoot` / `salary_tender_duplicate_root`,
  предел глубины 5, защита от циклов).
- **Отменённый дубль.** Финальные статусы отмены («Отмена: Дубль на тендер», «Нет таких
  позиций») в ОП практически не проставляют — отмены копятся в «Согласовании отмены»,
  а вот **причину отмены заполняют**. Поэтому и дубль, и «не наша продукция» ловятся
  статусом **или** причиной отмены.
- **Эталон выиграл.** Забрав закупку, эталон уходит в производство и дальше по воронке —
  «тендерного» статуса у него уже нет. Правомочность даёт и это: `wonProduction` /
  `salary_order_won_production` (история перехода в closing-статус либо текущий статус),
  та же канва, что у членства в числителе.

### Смета (`estimate_rule`, август 2026)

Клиент не покупает, а запрашивает цену, чтобы заложить её в бюджет на далёкое будущее
(закупка через год-два или без срока). Продажи тут не было и быть не могло, но в
знаменателе конверсии такой заказ стоит наравне с реальной заявкой.

Правило работает **только внутри `statuses`** — по требованию бизнеса это «Согласование
отмены»; в «Отложено» и прочие статусы намеренно не лезет, хотя сметы там встречаются.
Две ветки, обе описаны в `lib/salary/estimates.ts` + `migrations/20260803_salary_estimate_exclusion.sql`:

1. **Причина отмены «Смета»** (`calc_rate`) — явный выбор менеджера из справочника CRM,
   исключает сразу, без ИИ.
2. **Слово-маркер в комментарии** (`смет`, `бюджетир`) — сам по себе шумный
   («не работают по сметам», «запрос сметы был»), поэтому требует **подтверждения по
   диалогу**: вердикт классификатора в `order_estimate_verdicts` с
   `is_estimate = true` и `confidence >= min_confidence`.

Вердикта нет (звонков не было, расшифровки пустые) — заказ **остаётся** в конверсии.
Это встроенный контроль злоупотребления, как у дублей: молчание не считается доказательством.

Почему ветки именно такие (разбор 6 месяцев, `scratch/probe-smeta*.mjs`): из 77 кандидатов
в «Согласовании отмены» 58 имеют причину «Смета», 38 — маркер в тексте, а **пересечение
всего 19** — сигналы почти не дублируют друг друга. Транскрипты при этом есть лишь у 47%
кандидатов, так что требовать ИИ-подтверждение для обеих веток значило бы не исключить
половину смет.

Классификатор: `lib/salary/estimate-classifier.ts` + воркер
`app/api/cron/system-jobs/salary-estimate-classify` (каждые 15 мин). Читает расшифровки
звонков заказа (`call_order_matches` → `raw_telphin_calls.transcript`), промпт — в
`ai_prompts` (`salary_estimate_classifier`), редактируется в `/settings/prompts`.
Когда очередь пуста, воркер **сам добирает бэклог** (`findEstimateCandidates`) — врезки в
горячий путь синка заказов нет. Расчёт ЗП модель не вызывает: читает только готовый вердикт.

⚠️ В SQL сравнения с причиной отмены обязаны идти через `COALESCE(..., '')`: у большинства
заказов поле пустое, и `NULL` внутри `NOT (...)` выбрасывает строку из знаменателя целиком
(на июле знаменатель схлопывался с 271 до 44).

**Гейт зеркальности** — `npx tsx -r dotenv/config scripts/salary_verify_duplicate_rule.ts
dotenv_config_path=.env.local`: прогоняет месяц через TS-правило и через RPC и сравнивает
множества исключённых. Гонять после ЛЮБОЙ правки правила, в TS или в SQL.

## 4. Бонус-блоки (каталог)
Блок = дескриптор в коде (`code, name, methodology, kind, group, multiplierScope?, requiredMetrics, paramSchema`)
+ чистая `compute(m, params, ctx) → {amount|multiplier, explain, tariff, dataFill}`. Параметры (числа) — из БД.

**`tariff` (ставки в отчёте).** Блок обязан возвращать `tariff: TariffLine[]` — свои ставки/пороги/
ступени ИЗ `params`, человеческим языком (`{label, value, active?}`; `active` = ступень, по которой
шёл расчёт месяца). Разделение ролей: `explain` = «что получилось в этом месяце», `tariff` = «по каким
числам считают». Хелперы — `lib/salary/blocks/tariff.ts` (`tierLines`, `thresholdLine`). Едет в
`breakdown.blockContributions[].tariff` и рендерится общим `components/salary/BlockBreakdown.tsx`
(раскрытие «Тариф» под строкой блока) в `/salary/my`, отчёте менеджера и отчёте инженера.
Новый блок без `tariff` = менеджер не видит своих ставок — добавлять сразу. Гейт —
`tests/salary-compose.test.ts` (блок «тариф: …»). У ЗАКРЫТЫХ периодов, посчитанных до этой правки,
`tariff` в снимке `salary_calc` нет — раскрытие просто не показывается (не ошибка).

**Роли композиции:**
- `kind`: `base | premia | variable | multiplier | penalty`
- `group` (куда падает аддитив): `base | premia | variable | flat | duty`
- `multiplierScope` (для множителей): `premia` (множит премию) | `variableBracket` (множит скобку)

**Алгоритм сборки** (`lib/salary/blocks/compose.ts`):
```
total = base
      + (premia × Π(множители scope=premia) + variable) × Π(множители scope=variableBracket)
      + flat + duty + penalty
```
Под пресетом «Продавец» это тождественно прежней жёсткой формуле — закреплено golden-тестом
`tests/salary-compose.test.ts` (запускать в CI).

**Реализованные блоки** (`core-blocks.ts` + `extra-blocks.ts`, регистрируются в `registry.ts`):

| code | Название | kind/group | Метрики | Заметка |
|---|---|---|---|---|
| `oklad` | Оклад | base/base | worked_days | пропорция по отработанным дням (см. ниже об источнике дней) |
| `premia_zayavki` | Премия за заявки | premia/premia | counted_orders, order_type | ставки new/permanent |

> модели держать в уме, где бонус должен/не должен умножаться.

### Доплата за повторную покупку (`repeat_client_bonus`, август 2026)

Цель — уйти от оплаты «за поток заявок» к оплате за возврат клиента: превращение разового
покупателя в постоянного. Список порогов задаётся в конструкторе схем строками
«какая по счёту покупка → сколько ₽», поэтому платить можно за 2-ю, 3-ю, 6-ю или любую другую —
в коде номеров нет.

**Номер покупки считается на момент входа заказа в производство** (RPC
`salary_client_purchase_ordinals`, оконная функция по возрастанию даты), а не «сколько сделок у
клиента сейчас». Иначе выплата мигала бы задним числом: клиент купил третий раз в августе — и
мартовский заказ внезапно стал бы третьим. Этим же блок отличается от `premia_zayavki`, где тип
«новый/постоянный» берётся из общего числа сделок (`salary_client_deal_counts`).

**Интервал между покупками не проверяется** — решение бизнеса (август 2026): важен сам факт
возврата клиента, а не то, как быстро он вернулся.

Воронка на момент внедрения (2025-01…2026-08, `scratch/probe-final.mjs`): 1-я покупка — 823
клиента, 2-я — 128, 3-я — 35, 6-я — 6. Главный провал на переходе **1→2** (отваливается 84%),
поэтому доплату за 2-ю покупку стоит рассматривать наравне с 3-й — событий там втрое больше.

**Отработанные дни для оклада — два источника, приоритет у ручного** (`metrics.ts`):
1. **Табель** `salary_duty` (`kind='worked_day'`, UI «Табель») — если по менеджеру за месяц есть записи,
   считаем строго по ним.
2. **Отпуска/отсутствия** — если табеля нет: `worked = рабочие дни месяца − рабочие дни отсутствия`.
   Источник ЕДИНЫЙ с модулем распределения заявок («Катерина», таблица `email_intake_absences`,
   UI «Отпуска/отсутствия»): по тем же отметкам менеджер выпадает из распределения новых клиентов.
   **Второго журнала отпусков в ЗП не заводить.**
3. Нет ни того, ни другого → `workedDays = null` → оклад полный.

Режется **только оклад** (`group: base`): заказы, обработанные в отпуске, считаются как обычно —
премия за заявки и бонусы по ним начисляются полностью. В отчёте это видно в explain блока
(«Оклад 30 000 ₽ × 13 из 23 рабочих дней, отсутствие 10 дн.»), в дашборде — отдельным флагом.

**Политика по плану отдела (решение 2026-07-29):** `dept_plan_coef` мотивирует **только вверх**
(≥100% → ×1.2, ниже → ×1.0). Вниз режет **только личный план** (`plan_coef`). Причина: множители
`variableBracket` перемножаются, а план отдела = сумма личных, поэтому старые понижающие ступени
(≥95% → ×0.9, ≥70% → ×0.6, ниже → ×0) штрафовали одну и ту же недоработку дважды и одинаково били
по тому, кто свой план сделал, и по тому, кто его провалил. Июль 2026: менеджер с личным выполнением
91% получал ×0.8 × ×0.6 = ×0.48. Не возвращать понижающие ступени в `dept_plan_coef` без явного
решения; если нужен командный штраф — делать его асимметричным (масштабировать личным выполнением).

**Грабли тиров (открыто, чинить осознанно):**
- Значение **ниже самого нижнего порога** → `pickTier` возвращает `null` → фолбэк **×1**, а не нижний
  тир. У `plan_coef` нижняя ступень `{min:50,k:0}` и тира от 0 нет: 49% личного плана даёт полную
  премию, 50% — ноль. Лечится ступенью `{min:0,...}` в параметрах схемы.
- `k_team` и `dept_plan_coef` считают **одну метрику** (выручка отдела) в разных единицах (₽ и %
  плана) и перемножаются. В боевой схеме у `k_team` нет нижней ступени → вниз он не работает вообще.

**Доступность данных:** `metrics-catalog.ts` помечает метрики `full | partial | none`. Блок виден в
конструкторе только если все его метрики доступны. `margin` помечен `partial` (purchasePrice не у всех заказов).

## 5. Схемы (роли) и реестр
- **Схема** — именованный пресет блоков с параметрами, версионируется по дате
  (`salary_scheme` + `salary_scheme_block`).
- Менеджеру назначается схема (`salary_manager_comp`, effective-dated). **Есть назначение → в реестре ОП.**
- Сид (миграция `20260610_salary_schemes.sql`): «Продавец» (`seller`, полная мотивация, параметры = текущий
  `salary_config`) и «Оператор» (`operator`, только оклад 15 000). Назначения с 2026-05-01:
  Матвеева(98)/Парфёнова(10)/Гордеева(249) → seller; Хапилова(321) → operator.

## 6. Планы
`salary_plan` (помесячно): `manager_id NULL` = общий план отдела, иначе личный. Метрика — `revenue_no_vat`.
Личные и общий **независимы**. Редактируются в «Настройки мотивации → Планы».

## 6a. Грейды (ранг-множитель: накопление ИЛИ приз месяца)
Два режима, переключаются полем `mode` в политике (`GRADE_POLICY_SCHEMA`, `lib/salary/grades.ts`):

- **`streak`** (дефолт, обратная совместимость) — грейд как **состояние**: `floor` низший (по умолч. 3,
  ниже не падаем) … `top` высший (1). Растёт за выполнение показателей N месяцев **подряд**, откатывается
  за невыполнение подряд (`decideGrade`, `evaluateMonth`, `criteria[]`).
- **`monthly_prize`** — грейд как **приз по итогам месяца** (пилот с 2026-07-29): каждый месяц
  переустанавливается заново, накопления нет. `prize.gate` (обычно выполнение личного плана ≥100%)
  отсекает участников; среди прошедших место решает `prize.tiebreak` — приоритет показателей
  (первый решает, при равенстве следующий). Место k → уровень `topLevel + k − 1`, но не ниже
  `floorLevel`; гейт не прошёл (или нет метрик за месяц) → `floorLevel`. Гейт не прошёл никто → **все на полу**.
  Сравнение идёт внутри когорты (`cohort`). Функции: `assignMonthlyPrize` (чистая), `evaluatePrizeMonth`.
  **Почему так:** грейд-приз сознательно НЕ ранжирует по проценту плана (это уже делает `plan_coef`) —
  план работает гейтом, а место определяют качество и конверсия, иначе один показатель считается дважды.
- **Политика** — `salary_config['grade_policy']` (effective-dated, ноль хардкода): `mode`, `floorLevel`/
  `topLevel`, `cohort` (`scheme` — сравнение внутри роли, или `register`), плюс для `streak`:
  `lookbackMonths`, `promoteAfterMonths`/`demoteAfterMonths`, `criteria[]`; для `monthly_prize`: `prize`.
- **Состояние** — леджер `salary_grade` (effective-dated, как `salary_manager_comp`): текущий грейд на
  период = последняя запись с `effective_from ≤ 1-е число месяца. `salary_grade_eval` — кэш помесячной
  оценки «зачтён/нет» (прозрачность отчёта).
- **Пересчёт** (`recomputeGrades`): по итогам месяца M грейд вступает в силу с **M+1** (сами периоды не
  мутируются, циркулярности нет). Идемпотентно (UNIQUE `manager_id,effective_from`). В `streak` пишем
  только изменившиеся строки, в `monthly_prize` — **строки по всему реестру каждый месяц** (иначе грейд,
  не подтверждённый новым месяцем, не скатится на пол).
  Cron: `app/api/cron/system-jobs/grade-eval` (ежедневно) берёт последний **закрытый** период, но не
  старше прошлого календарного месяца — иначе без закрытий механика молчала бы вечно (так и было:
  все периоды `open` → `no_closed_period`, `salary_grade_eval` пустая, все грейды выставлены руками).
  Ответ содержит `basis` (`closed_period` | `last_calendar_month`) и `mode`.
- **Применение** — блок `grade_multiplier` (multiplier/variableBracket): читает `ctx.managerGrade`
  (резолв `resolveManagerGrades(asOf)` в движке) → коэффициент из своих `tiers` (`level→k`). Опционален
  в схеме; нет блока → грейд не влияет. Грейд множит **переменную часть** (как К_команды).

    коэффициент отдельной строкой с рублёвым эффектом** (эффект = последовательное применение множителей:

## 10. Обратная совместимость
Движок маппит вклады блоков обратно в legacy-колонки `salary_calc` (oklad/premia_zayavki/k_quality/...),
поэтому дашборд/экспорт работают без изменений. Новые блоки (план/объём/SPIFF) идут в `total` и
`breakdown.blockContributions[]`. Старые `breakdown` без `blockContributions` — отчёт читает legacy-поля (фолбэк).

## 11. Как сделать (рецепты)
- **Новый блок:** реализовать `BonusBlock` в `core-blocks.ts`/`extra-blocks.ts` (объявить `requiredMetrics`
  из `metrics-catalog`; если данных в каталоге нет — сперва добавить метрику и её сбор в `metrics.ts`),
  зарегистрировать в `registry.ts` (+ `DEFAULT_BLOCK_PARAMS`). Числа — только в params, не в коде.
- **Новая схема / правка:** UI «Схемы» (или `PUT /api/salary/schemes`). Версия с `effective_from`.
  **Смена даты у открытой версии создаёт НОВУЮ версию, прежняя остаётся** — прошлый месяц
  продолжает считаться по правилам, что действовали тогда. Правка без смены даты меняет
  ту же версию (upsert по `code,effective_from`). До августа 2026 `saveScheme` при смене даты
  **удалял** исходную версию («перенос даты»): роль с 01.02.2026, переведённая на 01.08.2026,
  оставляла февраль–июль вообще без схемы — менеджеры выпадали из реестра, ведомость за июль
  обнулялась. Не возвращать это поведение.
- **Просмотр истории мотивации:** в шапке роли — выпадающий список версий (`listSchemeVersions`,
  отдаётся в `GET /api/salary/schemes` полем `versions`). Выбор версии открывает её состав блоков:
  так видно, по каким правилам считался любой прошлый месяц. Список включает и будущие версии
  (мотивация «с 1-го числа следующего месяца» — обычное дело), поэтому по `asOf` не фильтруется.
- **Удалить роль:** кнопка-корзина в шапке роли (или `DELETE /api/salary/schemes?code=…`). Если по роли уже
  считалась ЗП (есть `salary_calc` с `breakdown->>'schemeCode' = code`) — роль не удаляется, а **архивируется**
  (`salary_scheme.archived_at`): прячется из активного конструктора, история и пересчёт прошлых периодов
  сохраняются. Иначе — полное удаление (версии + блоки каскадом + назначения). Восстановление из «Архива ролей»
  (`POST /api/salary/schemes {action:'restore_scheme', schemeCode}`).
- **В/из реестра:** UI «Реестр ОП» (или `POST /api/salary/schemes` assign/unassign).
- **План:** UI «Планы» (или `PUT /api/salary/plans`).
- **Пересчёт месяца:** кнопка «Пересчитать» (или `POST /api/salary/recalc`). Закрытый период не пересчитывается.

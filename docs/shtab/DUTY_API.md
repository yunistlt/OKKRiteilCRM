# Служебный API Штаба для консультанта ЦехУспеха

Программы Штаба закрепляются за постами, посты занимают люди, и человеку нужно
помогать их выполнять. Помогает консультант, который уже живёт в ЦехУспехе — там,
где начальник цеха работает каждый день. **Штаб отдаёт данные, голос и характер
остаются за консультантом.**

Этот документ — договор между системами. Он написан для той стороны, которая
прицепляет консультанта к окну.

## Что отдаётся и чего не отдаётся

Отдаётся **только то, что относится к самому человеку**: программы его поста, их
задачи, сроки, что он сам сказал по задачам.

Не отдаётся ничего из остального Штаба: ни реестра минусов, ни приоритетной
области, ни текста стратегии, ни чужих программ. Штаб закрыт ролью `admin` не из
вредности — там лежат все проблемы компании, включая кадровые и финансовые.
Этот слой существует, чтобы отдать человеку его работу, а не приоткрыть Штаб.

Изоляция проверена на живой базе: два поста с разными программами не видят задач
друг друга, а попытка отчитаться по чужой задаче отклоняется с 403.

## Доступ

Все маршруты закрыты общим токеном системы: заголовок
`Authorization: Bearer <SHTAB_DUTY_TOKEN>`.

Токен подтверждает, что запрос пришёл **из ЦехУспеха**. Кто именно спрашивает,
говорит параметр `uid` — идентификатор занимающего пост. Разделять эти две вещи
важно: на токене одном права строиться не могут.

Токен задаётся переменной окружения `SHTAB_DUTY_TOKEN` (не короче 24 символов) на
стороне Штаба. **В чат его не присылать.**

## Как человек опознаётся

В Штабе у каждого поста есть поле `external_uid` — идентификатор занимающего его
человека в ЦехУспехе. Заполняет владелец: вкладка «Цели и посты», колонка
«Занимает и кто он в ЦехУспехе».

Чем именно будет этот идентификатор — учётной записью, табельным номером или
почтой, — **решает ЦехУспех**. Со стороны Штаба это строка, и сравнивается она как
есть, без нормализации. Скажите, что вы будете присылать, и владелец впишет то же
самое.

Если пост с таким `uid` не заведён, ответ придёт с `known: false` и объяснением.
Консультант должен сказать это человеку прямо, а не делать вид, что задач нет.

## GET /api/duty/tasks?uid=…

Всё, что относится к человеку.

```json
{
  "known": true,
  "post": {
    "id": 3,
    "title": "Начальник цеха по производству",
    "holder": "Сергей",
    "idealScene": "Такт держится, оборудование обслуживается по графику",
    "statistic": "выпуск за смену"
  },
  "programs": [
    {
      "programId": 2,
      "block": "Пропускная способность покраски",
      "mainTask": "Покраска устойчиво пропускает объём, соответствующий такту…",
      "status": "active",
      "tasks": [
        {
          "id": 11,
          "kind": "rabochaya",
          "kindTitle": "Рабочие задачи",
          "kindHint": "шаги к результату, посчитанные обратным отсчётом",
          "ordinal": 1,
          "text": "Замерить пропускную способность за пять смен подряд.",
          "why": "",
          "metric": "",
          "target": "",
          "fact": "",
          "sourceNote": "",
          "done": false,
          "dueOn": "2026-09-05",
          "overdue": false,
          "lastReport": { "kind": "stuck", "text": "нет материала", "at": "2026-08-28T10:00:00Z" }
        }
      ],
      "stuck": [
        { "taskId": 11, "text": "Замерить пропускную способность…", "said": "нет материала", "days": 3 }
      ]
    }
  ]
}
```

Что важно знать про поля:

- `kind` — один из пяти типов задач: `pervoocherednaya`, `zhiznenno_vazhnaya`,
  `rabochaya`, `proizvodstvennaya`, `uslovnaya`. Русские названия и подсказки уже
  приложены (`kindTitle`, `kindHint`) — их не надо переводить у себя.
- **`why` у жизненно важных задач обязательно показывать.** Это правило,
  нарушение которого убивает программу, и без причины оно нарушается при первом
  же давлении сроков.
- У производственных задач `target` может быть **пустым**, и это законно — тогда
  заполнен `sourceNote`: каким замером и на каком шаге число закрывается.
  Пустое число со ссылкой на замер — это план работы, а не пропуск в данных.
  Придумывать вместо него значение нельзя.
- `stuck` отсортирован от самого давнего. С него начинается ежедневная планёрка:
  `days` показывает, сколько дней задача стоит.
- `overdue` считается по сроку связанного проекта; у задач без проекта `dueOn` пуст.

## POST /api/duty/report

Человек отчитался по задаче.

```json
{ "uid": "cu-1001", "task_id": 11, "kind": "stuck", "text": "нет материала для ремонта" }
```

- `kind`: `done` — сделал, `stuck` — застрял, `note` — сказал по делу.
- `done` ставит отметку о выполнении, `stuck` **снимает** её: человек сказал, что
  задача не закрыта, и держать её выполненной значит врать сводке владельца.
- При `stuck` текст обязателен: «застрял» без объяснения нечего разбирать на
  планёрке. Придёт 400 с внятным сообщением.
- Чужая задача → 403. Принадлежность проверяется на каждой записи, а не только
  при чтении: зная чужой номер задачи, иначе можно было бы отметить её
  выполненной.

Ответ: `{ "ok": true, "report_id": 42 }`.

## GET /api/duty/knowledge?q=…

Выдержки из базы знаний под вопрос человека — то, чем консультант помогает по
существу.

```json
{
  "found": 3,
  "articles": [
    {
      "title": "Как замерить пропускную способность передела",
      "content": "…",
      "source": "Практика производственного замера — изложение своими словами",
      "similarity": 0.71
    }
  ]
}
```

В базе лежат статьи по ремеслу (`craft`) — как найти узкое место, замерить
пропускную способность, составить график ТО, выбрать подрядчика, пройти маршрут
заготовки, разметить зоны, написать регламент, ознакомить людей, поставить
наставничество, посчитать штатную потребность — плюс методичка «Альянс Стратег» и
управленческий канон.

**Фактов о компании здесь нет и быть не может.** Это способы делать, а не данные.
Задачи человека берутся отдельным запросом.

`source` показывать обязательно: консультант называет, откуда мысль, а не выдаёт
чужую за свою.

## Что нужно с вашей стороны

1. Сказать, каким будет `uid` — что именно вы пришлёте в запросах.
2. Прицепить три вызова к окну консультанта.
3. Показывать `why` у жизненно важных задач и `source` у выдержек.
4. Не подставлять число вместо пустого `target` — вместо этого сказать человеку,
   каким замером оно закрывается (`sourceNote`).

## Что нужно со стороны Штаба

1. Применить `migrations/20260828_shtab_duty.sql`.
2. Задать `SHTAB_DUTY_TOKEN` в переменных окружения Vercel.
3. Заполнить `external_uid` у постов и закрепить программы за постами
   (вкладка «Программы», строка «Ведёт пост»).

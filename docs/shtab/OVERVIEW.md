# Штаб владельца

Рабочее место собственника по методологии «Альянс Стратег». Не дашборд: владелец
здесь пишет анализ сам, а система считает то, что можно посчитать, и не даёт
перескочить через шаги.

Маршрут `/shtab`, доступ — только роль `admin` (`lib/rbac.ts`). В разделе лежат все
проблемы компании, включая кадровые и финансовые, поэтому он закрыт наглухо.

## Методология в двух абзацах

Десять компонентов управления упорядочены по силе воздействия: долгосрочная цель →
краткосрочная цель → политика → планы → проекты и приказы → оргполитика → статистики
→ ЦКП → пост → стратегия. Работа идёт снизу вверх от симптомов к причинам.

Рабочий цикл: выписать все минусы → разложить по областям → область с наибольшим
числом минусов и есть приоритет → самый жирный минус развернуть в ситуацию → найти
«почему» и проверить его тремя критериями (внутри организации, устранима имеющимися
ресурсами, даёт облегчение) → сформулировать краткосрочную цель из двух частей
(улаживание + кусок долгосрочной цели) → собрать карту ресурсов → написать стратегию
повествованием в повелительном наклонении.

## Что считает система, а что пишет владелец

**Считает сама:**
- приоритетную область — по числу открытых минусов, мнения в расчёте не участвуют
  (`topArea` в `lib/shtab/types.ts`);
- прогресс разбора по шести шагам (`razborProgress` там же);
- вердикт по статистике — сигнал это или шум (`lib/shtab/xmr.ts`);
- подсказку области по тексту минуса (`guessArea` в `lib/shtab/checks.ts`);
- черновик стратегии и заготовки проектов из карточек (`lib/shtab/strategy.ts`);
- приход группы по месяцам из выписок Точки и Т-Банка (`lib/shtab/income.ts`).

**Пишет владелец:** ситуацию, «почему», обе части краткосрочной цели, названия
ресурсов, саму стратегию, проекты со сроками, посты, три долгосрочные цели.

**Проверяет наставница Тамара** (`lib/shtab/checks.ts`) — три ошибки, которые в
методичке названы прямо: причина вне организации, ярлык вместо развёрнутой ситуации,
обобщённый ресурс («деньги» вместо «180 тыс. руб. на вторую камеру полимеризации»),
проект без ответственного или срока, пост без статистики или со статистикой,
которую дорого считать. Это правила, а не ИИ: никаких обращений к модели раздел
не делает.

## Модель данных

Миграция `migrations/20260825_shtab_owner_hq.sql`, аддитивная и идемпотентная.
Штаб один на компанию — строки не привязаны к пользователю.

| Таблица | Что хранит |
|---|---|
| `shtab_area` | справочник областей: `code`, `title`, `ordinal` |
| `shtab_minus` | реестр минусов; `source` = `owner` / `data` / `telegram` |
| `shtab_razbor` | разборы; `check_*` трёхзначны, `NULL` — ещё не отвечали |
| `shtab_resource` | колонки карты: `missing` и массив `available` |
| `shtab_razbor_minus` | какие минусы разбор берётся закрыть своей стратегией |
| `shtab_project` | проекты из стратегии: ответственный, срок, статус |
| `shtab_post` | посты: образцовое положение дел и еженедельная статистика |
| `shtab_goal` | три долгосрочные цели: `company`, `owner`, `product` |

Коды технические, подписи в справочниках: в логике сравнивается только
`code`/`source`/`status`, русские строки приходят из базы.

Три операции идут через функции БД, а не пачкой запросов, потому что сбой в
середине оставил бы данные в неверном состоянии, а тело функции выполняется в
одной транзакции:

- `shtab_set_resources(bigint, jsonb)` — перезапись карты ресурсов; иначе сбой
  между удалением и вставкой стирал бы собранную руками карту;
- `shtab_set_razbor_minuses(bigint, bigint[])` — набор закрываемых минусов;
- `shtab_close_razbor(bigint)` — закрытие разбора вместе с его минусами. Двумя
  запросами сбой оставил бы разбор закрытым, а минусы открытыми: реестр врал бы,
  и приоритетная область считалась бы по неверным числам.

**Сид:** 42 реальных минуса, снятых с владельца на разборе, разложены по 11 областям
(Производство 14, Управление 8, Финансы 4, Внедрение ИИ 4, Продажи 3, HR 3, Закупки 2,
Разработка КД 2, Маркетинг 1, Юридический 1, Бухгалтерия 0). Заливаются один раз:
если в таблице уже что-то есть, блок не выполняется — иначе закрытые минусы воскресали
бы при каждом повторном прогоне.

## Устройство раздела

```
app/shtab/page.tsx        оболочка: вкладки, колонка Тамары, загрузка состояния
app/shtab/useShtab.ts     состояние и запись в базу (правки текста — с задержкой)
app/shtab/Tamara.tsx      фигура двумя слоями, очередь реплик, восемь состояний
app/shtab/shtab.css       вся вёрстка раздела, каждое правило под .shtab
app/shtab/views/          девять экранов
lib/shtab/                доменная логика: xmr, checks, strategy, income, types
app/api/shtab/            state, minus, razbor, project, post, goals, stats
```

Стили лежат обычным CSS-файлом, а не Tailwind: у раздела своя типографика и своя
палитра, и переписывать 400 строк в утилитарные классы значило бы потерять то, ради
чего эта вёрстка делалась. Все правила начинаются с `.shtab`, поэтому наружу ничего
не течёт. Шрифты самохостятся через `next/font` (`app/shtab/fonts.ts`).

Раздел светлый: приложение не имеет тёмной темы (`--background: 255 255 255` в
`app/globals.css`), и вторая тема только в одном разделе была бы разнобоем.

## Тамара

Фигура — утверждённый фотокадр, разрезанный на два слоя: `public/images/tamara/body.webp`
и `head.webp`. Слои двигаются раздельно (тело дышит и переносит вес, голова дрейфует
и поворачивается под состояние), потому что голова — то, что глаз считывает как
«живая». Нарезка воспроизводится скриптом `scripts/shtab-cut-tamara-layers.py`.

Восемь состояний: `idle`, `listening`, `thinking`, `object`, `explain`, `approve`,
`alert`, `away`. Сейчас они выражаются позой и темпом дыхания. Настоящее движение —
моргание, мимика, дыхание грудной клетки — придёт с восемью видео-петлями; тексты
заказа лежат на вкладке «Тамара» внутри раздела.

Кроме проверок методички Тамара отвечает на вопросы о положении дел и раз в
неделю сама приносит сводку. Всё, что она говорит о компании, приходит из
инструментов; знания по управлению лежат в базе с поиском по смыслу. Подробно —
[docs/shtab/TAMARA.md](TAMARA.md).

## Статистики: что подключено, а что нет

Подключена одна — **приход группы** по месяцам. Источник `point_payments`:
выписки Точки и Т-Банка по всем юрлицам. Из суммы исключаются платежи со
статусом `ignored` — переводы между своими счетами и банковские операции;
включать их значит раздувать приход собственными деньгами, гоняемыми по кругу.

Метрика называется приходом, а не денежным потоком, намеренно. Потока в данных
нет: `lib/payments/tbank.ts` пишет в базу только входящие операции, расходов там
физически не существует. Считать поток из одних приходов — выдавать выручку за
прибыль.

Три оставшиеся строки — заглушки с подписанным будущим источником:

- **Объём произведённой продукции** — ЦехУспех, коннектора нет.
- **Рекламации от отгруженного** и **Количество постоянных клиентов** —
  считаются по `orders`, `statuses` и `salary_client_canon`. Эти таблицы созданы
  прямо в Supabase, и **в `migrations/` их определений нет**: локально схему не
  воспроизвести, а значит запрос не проверить. Раздел, показывающий
  правдоподобное, но непроверенное число, хуже раздела, который честно говорит
  «данных мало» — на этом стоит вся его конструкция.

Реестр метрик — `app/shtab/stats.ts`. Подключить строку значит сменить у неё
`source` на `'api'` и добавить запрос в `app/api/shtab/stats/route.ts`.

## Чего ещё нет

- **Напоминания снаружи.** Понедельничная сводка Тамары появилась
  (`/api/cron/shtab-briefing`), планёрки ставятся в Google Calendar
  (`/api/cron/shtab-rhythm`), но толчка в мессенджер или Telegram пока нет.
- **Приказов.** Проект есть, приказа как отдельного документа — нет.
- **Факта по производственным задачам.** Число цели у программы есть, факт
  вводится вручную: цеховых замеров (пропускная способность, простои, некомплект)
  нет ни в одном подключённом источнике.
- **Истории статистик по постам.** Пост хранит, что считаем, но ряд по нему не
  собирается: для этого нужен ввод чисел или коннектор под каждую статистику.

## Проверка

```bash
npm run build                                   # он же проверка типов
npx vitest run tests/shtab-*.test.ts
```

Миграция применяется одной командой (раннера миграций в проекте нет, поэтому
скрипт свой):

```bash
npm run shtab:migrate
```

Берёт `DATABASE_URL` (или `POSTGRES_URL`) из `.env.local`, применяет
`migrations/20260825_shtab_owner_hq.sql` и печатает, что встало в базу.
Повторный прогон безопасен: миграция аддитивная и идемпотентная.

Миграция Тамары применяется так же — файл `migrations/20260826_shtab_tamara.sql`,
после неё нужен засев знаний:

```bash
npm run shtab:seed-kb
```

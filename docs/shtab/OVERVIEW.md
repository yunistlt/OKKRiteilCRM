# Штаб владельца

Рабочее место собственника по методологии «Альянс Стратег». Не дашборд: владелец
здесь пишет анализ сам, а система считает то, что можно посчитать, и не даёт
перескочить через шаги.

Маршрут `/shtab`, доступ — только роль `admin` (`lib/rbac.ts`). В разделе лежат все
проблемы компании, включая кадровые и финансовые, поэтому он закрыт наглухо.

## Методология в двух абзацах

Десять компонентов управления упорядочены по силе воздействия: долгосрочная цель →
краткосрочная цель → политика → планы → проекты и приказы → оргполитика → статистики
→ ЦКП → пост → стратегия. Работа идёт снизу вверх от симптомов к причинам.

Рабочий цикл: выписать все минусы → разложить по областям → область с наибольшим
числом минусов и есть приоритет → самый жирный минус развернуть в ситуацию → найти
«почему» и проверить его тремя критериями (внутри организации, устранима имеющимися
ресурсами, даёт облегчение) → сформулировать краткосрочную цель из двух частей
(улаживание + кусок долгосрочной цели) → собрать карту ресурсов → написать стратегию
повествованием в повелительном наклонении.

## Что считает система, а что пишет владелец

**Считает сама:**
- приоритетную область — по числу открытых минусов, мнения в расчёте не участвуют
  (`topArea` в `lib/shtab/types.ts`);
- прогресс разбора по шести шагам (`razborProgress` там же);
- вердикт по статистике — сигнал это или шум (`lib/shtab/xmr.ts`);
- подсказку области по тексту минуса (`guessArea` в `lib/shtab/checks.ts`);
- черновик стратегии из карточек в порядке очереди (`lib/shtab/strategy.ts`).

**Пишет владелец:** ситуацию, «почему», обе части краткосрочной цели, названия
ресурсов, саму стратегию, три долгосрочные цели.

**Проверяет наставница Тамара** (`lib/shtab/checks.ts`) — три ошибки, которые в
методичке названы прямо: причина вне организации, ярлык вместо развёрнутой ситуации,
обобщённый ресурс («деньги» вместо «180 тыс. руб. на вторую камеру полимеризации»).
Это правила, а не ИИ: никаких обращений к модели раздел не делает.

## Модель данных

Миграция `migrations/20260825_shtab_owner_hq.sql`, аддитивная и идемпотентная.
Штаб один на компанию — строки не привязаны к пользователю.

| Таблица | Что хранит |
|---|---|
| `shtab_area` | справочник областей: `code`, `title`, `ordinal` |
| `shtab_minus` | реестр минусов; `source` = `owner` / `data` / `telegram` |
| `shtab_razbor` | разборы; `check_*` трёхзначны, `NULL` — ещё не отвечали |
| `shtab_resource` | колонки карты: `missing` и массив `available` |
| `shtab_goal` | три долгосрочные цели: `company`, `owner`, `product` |

Коды технические, подписи в справочниках: в логике сравнивается только
`code`/`source`/`status`, русские строки приходят из базы.

Карта ресурсов перезаписывается целиком через функцию `shtab_set_resources(bigint,
jsonb)`. Так сделано намеренно: «удалить и вставить» двумя отдельными запросами
означало бы, что сбой между ними стирает собранную руками карту, а тело функции
выполняется в одной транзакции.

**Сид:** 42 реальных минуса, снятых с владельца на разборе, разложены по 11 областям
(Производство 14, Управление 8, Финансы 4, Внедрение ИИ 4, Продажи 3, HR 3, Закупки 2,
Разработка КД 2, Маркетинг 1, Юридический 1, Бухгалтерия 0). Заливаются один раз:
если в таблице уже что-то есть, блок не выполняется — иначе закрытые минусы воскресали
бы при каждом повторном прогоне.

## Устройство раздела

```
app/shtab/page.tsx        оболочка: вкладки, колонка Тамары, загрузка состояния
app/shtab/useShtab.ts     состояние и запись в базу (правки текста — с задержкой)
app/shtab/Tamara.tsx      фигура двумя слоями, очередь реплик, восемь состояний
app/shtab/shtab.css       вся вёрстка раздела, каждое правило под .shtab
app/shtab/views/          восемь экранов
lib/shtab/                доменная логика: xmr, checks, strategy, types
app/api/shtab/            state (GET), minus, razbor, goals
```

Стили лежат обычным CSS-файлом, а не Tailwind: у раздела своя типографика и своя
палитра, и переписывать 400 строк в утилитарные классы значило бы потерять то, ради
чего эта вёрстка делалась. Все правила начинаются с `.shtab`, поэтому наружу ничего
не течёт. Шрифты самохостятся через `next/font` (`app/shtab/fonts.ts`).

Раздел светлый: приложение не имеет тёмной темы (`--background: 255 255 255` в
`app/globals.css`), и вторая тема только в одном разделе была бы разнобоем.

## Тамара

Фигура — утверждённый фотокадр, разрезанный на два слоя: `public/images/tamara/body.webp`
и `head.webp`. Слои двигаются раздельно (тело дышит и переносит вес, голова дрейфует
и поворачивается под состояние), потому что голова — то, что глаз считывает как
«живая». Нарезка воспроизводится скриптом `scripts/shtab-cut-tamara-layers.py`.

Восемь состояний: `idle`, `listening`, `thinking`, `object`, `explain`, `approve`,
`alert`, `away`. Сейчас они выражаются позой и темпом дыхания. Настоящее движение —
моргание, мимика, дыхание грудной клетки — придёт с восемью видео-петлями; тексты
заказа лежат на вкладке «Тамара» внутри раздела.

## Чего ещё нет

Названо прямо, чтобы раздел не выглядел законченнее, чем он есть.

1. **Статистики на Пульте — заглушки.** Ряды в `app/shtab/stats.ts` демонстрационные,
   живых источников у них нет. У каждой строки подписан будущий источник, вердикт по
   коротким рядам честно говорит «данных мало». Подключение ЦехУспеха, склейки по ИНН
   и выгрузки Точки с Т-Банком — отдельная работа.
2. **Экрана проектов нет.** Стратегия заканчивается текстом; превращение её в проекты
   со сроками и ответственными не сделано.
3. **Связки «минус → закрыт какой стратегией» нет.** Разбор помнит, с какого минуса
   начался, но закрытие минуса стратегией не прослеживается.
4. **Посты не заведены.** Пост — не сотрудник: у него своё образцовое положение дел и
   своя еженедельная статистика. Под них нужна отдельная таблица и экран.

## Проверка

```bash
npm run build                                   # он же проверка типов
npx vitest run tests/shtab-xmr.test.ts tests/shtab-checks.test.ts
```

Миграция применяется вручную (раннера в проекте нет): выполнить
`migrations/20260825_shtab_owner_hq.sql` против `DATABASE_URL`. Повторный прогон
безопасен.

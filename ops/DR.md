## 1. Первым делом — сказать людям

Без этого остальное не имеет смысла: отдел должен знать, работать ему или ждать.
Сообщение в рабочий чат: что не работает, чем пользоваться пока, когда следующая весточка.

## 2. Лёг VPS обратного прокси

Приложение живо, не открывается только российский адрес.

1. В панели Timeweb (аккаунт cw271201) — перезагрузить VPS 5.42.111.117.
2. Не поднялся за 10 минут — временно перевести людей на адрес Vercel напрямую

3. Конфиг nginx — в `ops/reverse-proxy/`, разворачивается на чистый сервер по его README.

Внимание: на этом же VPS живут сторож конвейера и наш бэкап базы — после подъёма
проверить `/var/log/okk-watchdog.log` и `/var/log/okk-db-backup.log`.

## 3. Легла база

PITR у нас НЕ включён (решение 20.10.2026, $100/мес). Значит откат «на минуту назад»
невозможен, восстанавливаем из дампа. Два источника, берём тот, что свежее:

| Источник | Свежесть | Где |
|---|---|---|
| Наш дамп | до 2 часов | VPS, `/var/backups/okk-db/` |
| Бэкап Supabase | до 24 часов | Dashboard → Database → Backups |

### Путь А — средствами Supabase (проще, если жив их дашборд)

Database → Backups → **Restore to new project**. Получится новый проект со своим
ref, URL и ключами.

### Путь Б — из нашего дампа (если Supabase недоступен или их бэкап слишком стар)

```bash
# на VPS
ls -lt /var/backups/okk-db/            # выбрать нужный дамп
pg_restore --no-owner --no-privileges -d '<URL новой базы>' /var/backups/okk-db/okk-<дата>.dump
```

Новую базу поднять заранее некуда — создаём новый проект Supabase (или любой Postgres 17).

### Переключение приложения

Vercel → проект → Settings → Environment Variables → заменить на новые значения:

- `DATABASE_URL` (порт 6543, транзакционный пулер — как было)
- `POSTGRES_URL`, если задан
- `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`

Затем **Redeploy** (переменные подхватываются только новой сборкой).

После переключения не забыть:
- поменять `OKK_DB_URL` в `/etc/okk-db-backup.env` на VPS — иначе бэкапится мёртвая база;
- проверить, что кроны пошли: `/api/monitoring/pipeline-pulse` отдаёт 200;
- сверить номер сборки под логотипом — тот ли код на проде.

## 4. Встал конвейер, база жива

Сайт работает, но заявки/письма/расшифровки не двигаются.

1. `https://okk.zmksoft.com/api/monitoring/pipeline-pulse` — в теле `problems[]` написано,
   что именно встало, человеческим языком.
2. Частая причина (была 25.09.2026): на Vercel нет `CRON_SECRET` — все кроны получают 401
   и молчат. Проверить переменную, после правки — Redeploy.
3. Очередь разгребается сама, как только воркеры ожили. Руками ничего не перезапускать.

## 5. Чего НЕ делать

- Не чинить массовыми `UPDATE` по боевой базе в рабочее время — у базы слабый диск,
  16.10.2026 этим дважды уронили работу отдела.
- Не удалять старый проект Supabase, пока новый не отработал сутки.
- Не менять код «на ходу» во время аварии: сначала вернуть работу, потом разбираться.

## Что проверять раз в квартал

Учебное восстановление: поднять последний дамп в отдельную базу и убедиться, что ОКК
на ней стартует. Бэкап, который ни разу не разворачивали, бэкапом не считается.

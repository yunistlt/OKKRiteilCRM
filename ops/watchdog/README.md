# Внешний сторож конвейера

Крон на VPS, который следит, жив ли автомат ОКК, и пишет владельцу в Telegram, если
заявки перестали создаваться.

## Зачем снаружи, а не кроном Vercel

25.09.2026 крон-роуты закрыли проверкой ключа (`lib/cron-auth.ts`), а `CRON_SECRET` на
проде не завели. Планировщик Vercel три дня получал 401 — встали приём почты, очередь
работ и синхронизация заказов. Никто не заметил: заявки просто перестали появляться.
Сторож, который сам является кроном Vercel, в такой аварии умирает вместе со всеми
и молчит. Поэтому будильник вынесен на VPS обратного прокси — он переживает смерть
кронов, деплой и падение приложения целиком.

## Что проверяется

Эндпоинт `GET /api/monitoring/pipeline-pulse` (публичный, только отметки времени,
без клиентских данных) считает признаки жизни — `lib/pipeline-pulse.ts`:

| Проверка | Что смотрим | Когда это авария |
|---|---|---|
| Приём почты | `email_ingest_state.last_run_at` | пропущено 3 захода своего крона (но не меньше 30 мин) |
| Письма без разбора | самое старое `incoming_emails.status='new'` | ждёт дольше 2 ч |
| Очередь работ — по каждому типу | готовые `system_jobs` и последняя завершённая того же типа | исполнитель приходил по расписанию ≥2 раз и не взял ни одной; либо работает, но за 12 заходов не разгрёб хвост |

Ответ: `200` — жив, `503` — встал, в теле `problems[]` готовыми фразами. Кроме
`problems[]` в теле лежит `checks[]`, где у каждой проверки есть `verdict` и `reason` —
разбор причины человеческим языком, даже когда тревоги нет.

## Тревога только по поломке

17.10.2026, суббота: владельцу каждые 15 минут приходило «Конвейер ОКК встал — очередь
ничего не доделала за 13 ч». Накануне воркеры перевели на рабочее время
(`0 5,8,11,14 * * 1-5`), а норматив остался общий — «что-то должно доделываться каждые
45 минут». Сообщение, которое приходит, когда всё в порядке, перестают читать — и
пропускают настоящее.

Поэтому перед тревогой выясняется ПРИЧИНА молчания, и ответов три:

| Вердикт | Что значит | Тревога |
|---|---|---|
| `broken` | исполнитель по расписанию приходил и работу не взял | да |
| `waiting_schedule` | исполнителю ещё рано: ночь, выходной, раз в три часа | нет |
| `idle` | готовых работ нет — проверять нечего | нет |

**Расписание не заводится здесь руками и не «настраивается» заново.** Оно читается из
`vercel.json` — единственного места, где оно настоящее (`lib/system-job-workers.ts`
держит карту «тип работ → крон-роут», расписание берётся по этому пути). Поменяли крон —
сторож судит уже по новому, без единой правки в коде сторожа. Карту стережёт
`tests/system-job-workers.test.ts`: тип работ из роута воркера обязан быть в реестре, а
роут без крона — помечен снятым с производства.

Затор считается по ТИПУ работ, а не по самой старой записи в очереди: в очереди всегда
лежит хвост, который воркер пропускает (приоритет, ключ конкуренции). 28.09.2026 такой
хвост от 25-го был у четырёх типов, хотя воркеры в ту же минуту доделывали свежие работы —
проверка «по самой старой» горела бы вечно.

Проверки «Очередь работ ничего не доделала за 45 мин» больше нет: пустая очередь — это
тишина, а не авария. Проверки «Заказы из RetailCRM» нет с 05.10.2026 — приём выключен
решением владельца.

## Установка на VPS (5.42.111.117, Timeweb)

```bash
sudo mkdir -p /opt/okk-watchdog /var/lib/okk-watchdog
sudo cp okk-watchdog.py /opt/okk-watchdog/
sudo chmod +x /opt/okk-watchdog/okk-watchdog.py
```

Настройки — в `/etc/okk-watchdog.env` (права `600`, внутри токен бота):

```
OKK_PULSE_URL=https://okk.zmksoft.com/api/monitoring/pipeline-pulse
TELEGRAM_BOT_TOKEN=<токен @okkzmk_bot>
OWNER_CHAT_ID=<личка владельца, как в sales_rop_settings.owner_chat_id>
REPEAT_MINUTES=60
```

Крон раз в 15 минут (`sudo crontab -e`):

```
*/15 * * * * set -a; . /etc/okk-watchdog.env; set +a; /opt/okk-watchdog/okk-watchdog.py >> /var/log/okk-watchdog.log 2>&1
```

Проверка руками:

```bash
set -a; . /etc/okk-watchdog.env; set +a; /opt/okk-watchdog/okk-watchdog.py
```

## Поведение

- Авария → одно сообщение в личку, повтор не чаще `REPEAT_MINUTES` (по умолчанию час).
  Если список проблем изменился — сообщение уходит сразу, не дожидаясь часа.
- Починилось → одно сообщение «конвейер ожил».
- Сторож ничего не чинит и не запускает. Он только смотрит и зовёт человека.
- Telegram недоступен → пишет в лог и доживает до следующего захода, не падая.

## Если сторож сам замолчит

Он на том же VPS, что и nginx перед Vercel: если VPS лёг, сайт `okk.zmksoft.com` тоже
недоступен и это видно сразу. Отдельного сторожа за сторожем не ставим.

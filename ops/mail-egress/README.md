# Отправка почты через наш VPS (запасной путь)

## Что случилось 12.10.2026

Письма перестали уходить: `ETIMEDOUT 77.88.21.158:465`. Проверка связи прямо с
прода (`/api/monitoring/mail-health`, функции во Франкфурте):

| Куда | Результат |
|---|---|
| `smtp.yandex.ru:465` | таймаут 8 с |
| `smtp.yandex.ru:587` | таймаут 8 с |
| `imap.yandex.ru:993` | соединение за 39 мс |
| `smtp.gmail.com:465` | соединение за 3 мс |
| `smtp.mail.ru:465` | соединение за 105 мс |

Читается однозначно: у нашего сервера связь есть, другие почтовые серверы
отвечают мгновенно, **Яндекс молча роняет соединения именно к своему SMTP**.
Аккаунт не заблокирован — по IMAP тот же ящик работает. Значит фильтр по
адресам облака, а не по учётной записи.

## Чего не хватает для обхода

Наш VPS в Москве (`5.42.111.117`, тот же, что держит обратный прокси) к Яндексу
достучаться тоже не может, но по другой причине: **Timeweb закрывает исходящую
почту**. С VPS:

- `smtp.gmail.com:465`, `smtp.mail.ru:465` — таймаут (режет провайдер);
- `smtp.yandex.ru:465` — Connection refused.

Поэтому обход включается в два шага, и первый — не наш:

1. **Попросить Timeweb открыть исходящие 465/587** на сервере (заявка в
   поддержку из личного кабинета, аккаунт `cw271201`). Хостинги закрывают эти
   порты по умолчанию против спама и открывают по просьбе.
2. Поднять на VPS сквозной туннель и переключить приложение на него.

## Шаг 2, когда порты откроют

На VPS в `/etc/nginx/nginx.conf` (вне блока `http`):

```nginx
stream {
    server {
        listen 2465;
        proxy_pass smtp.yandex.ru:465;
        proxy_connect_timeout 10s;
    }
}
```

`nginx -t && systemctl reload nginx`. Трафик идёт насквозь: TLS остаётся
сквозным до Яндекса, пароль на VPS не виден и нигде не хранится.

Затем переменные Vercel:

```
SMTP_HOST = 5.42.111.117
SMTP_PORT = 2465
SMTP_SERVERNAME = smtp.yandex.ru
```

`SMTP_SERVERNAME` обязателен: сертификат остаётся яндексовым, и без пина имени
проверка сертификата не пройдёт. Код это уже умеет (`lib/email.ts`), правок не
нужно — только переменные и redeploy.

Проверка после включения: `/api/monitoring/mail-health` должен показать
соединение к `smtp.yandex.ru:465`, и письма из очереди уйдут сами.

## Пока не починено

Письмо, которое не удалось отправить, **не теряется**: оно встаёт в очередь
`email_scheduled_send` и уходит само, как только связь вернётся. Менеджеру об
этом сказано прямо в карточке. Срочное можно отправить из почтового ящика —
письмо всё равно попадёт в заказ: его подберёт чтение папки «Отправленные».
